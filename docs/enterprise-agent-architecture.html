Executive Brief

Three Decisions That Shape Everything

The architecture rests on three foundational choices. Each has a real cost-of-wrong-decision — get any one of them wrong and the system either doesn't scale, becomes brittle under load, or accumulates the kind of complexity that blocks future capability expansion.

①

Two Pillars, Not One

Analytics and process automation are architecturally incompatible if merged under a single orchestrator. Analytics is read-only, parallel, and embarrassingly stateless. Process automation has side effects, requires audit trails, demands human-in-the-loop approval, and runs asynchronously over hours or days. Separate orchestrators, separate deployment, separate auth scope — but unified session context at the enterprise layer.

②

Federated Orchestration, Not a God Agent

A single orchestrator that knows everything will become a bottleneck, a reliability single-point-of-failure, and an unmaintainable accumulation of routing logic within 12 months. The architecture uses a thin Enterprise Orchestrator for cross-pillar routing and session management, with thick domain-specific orchestrators that own their business logic completely.

③

Insight ≠ Query Answer

The existing system returns results. The new capability must return understanding. This requires a structurally different execution pattern: parallel fan-out to multiple data domains simultaneously, correlation with external market signals, and narrative synthesis that explains causality — not just reports metrics. This is not an incremental prompt change; it is a new architectural component: the Insight Engine.

What This Architecture Enables That Doesn't Exist Today

A restaurant GM can ask: "Why did my COGS spike 3 points last quarter?" — and receive: a cross-domain correlation (supply chain + finance + operational data), commodity price context from external market data, a comparison to same-store peers in the same region, and an automatically triggered procurement investigation workflow with an approval chain — all from a single natural language query, in under 30 seconds.

Honest Gap Analysis

What the Current Architecture Gets Right — and Where It Falls Short

Before designing the target state, it is necessary to be precise about what the existing design optimizes for, what it was never designed to do, and where extending it naively creates structural debt.

What's Right — Keep and Evolve

  • Domain SQL sub-agents — specialization reduces hallucination. A sales agent that only knows sales SQL is more reliable than a generalist. Keep this pattern, extend the domain coverage.
  • Orchestrator-worker topology — correct at its level. Anthropic's canonical pattern for breadth-first tasks. The pattern is right; the scope needs to expand.
  • Natural language → SQL intent classification — mature and working. Don't break it while adding insight generation on top of it.
  • Domain-specific prompts per agent — correct isolation of business context. Each agent's prompt should know its domain deeply and nothing else.

Critical Gaps — Must Address

  • Query dispatch ≠ insight generation. Current architecture returns data. Insights require cross-domain correlation + external context + causal reasoning. Adding a prompt to existing agents won't close this gap.
  • No agent identity layer. All agents likely share a service account. Process automation against Oracle Finance or SAP SuccessFactors requires per-agent credentials with scoped permissions. A finance agent cannot run under the same identity as an analytics agent.
  • No process automation design. Process agents have side effects. They require deterministic execution chains (for SOX/audit), checkpointing for long-running flows, and approval gates. The analytics orchestrator was designed for none of this.
  • No cross-regional data sovereignty handling. EU GDPR, APAC data residency laws, and NA compliance requirements differ materially. An agent that can query all regions uniformly is a compliance risk.
  • Context grows unbounded. No strategy for managing context accumulation across long multi-turn sessions. At enterprise scale with heavy usage, this is a latency and cost issue.
  • No external data integration. KPI analysis without commodity prices, macroeconomic indicators, or competitive benchmarks is incomplete. The data warehouse only holds what the company controls.

The Hidden Risk in "Just Extend the Current Architecture"

The existing query orchestrator is designed for read-only, stateless, reversible operations. Adding process automation sub-agents under the same orchestrator violates the fundamental contract of that design. When a finance process agent executes a journal entry or an HR agent triggers a termination workflow, the orchestrator must handle failure, rollback, approval gating, and audit in ways it was never built for. The blast radius of a routing error in the current system is a bad SQL query. In a process automation context, it could be an unauthorized financial transaction.

Architecture Principles

Seven Non-Negotiable Design Principles

These principles are derived from Anthropic, Google ADK, and OpenAI's published architecture guidance combined with enterprise-scale requirements unique to this context. Every architectural decision traces back to at least one of these.

P1 — Pillar Separation by Execution Contract

Analytics agents and process agents are governed by incompatible execution contracts (stateless read vs. stateful write with side effects). They must live in separate orchestration pillars with separate auth models, deployment units, and failure domains. Shared infrastructure (data access, session store, observability) is permitted; shared orchestration logic is not.

P2 — Thin Enterprise Orchestrator, Thick Domain Orchestrators

The Enterprise Orchestrator performs exactly one function: classify intent, route to the correct domain orchestrator(s), manage cross-pillar fan-out, and maintain session context. It contains zero business logic. Domain orchestrators own their routing, tool selection, and sub-agent lifecycle. Business logic cannot migrate upward into the enterprise layer — this is enforced by code review policy.

P3 — Centralized Catalog, Distributed Runtime

The Agent Registry is the single source of truth for agent capabilities, input/output schemas, SLA contracts, compliance tags, and ownership. But routing decisions use a locally cached copy of the catalog, refreshed on deployment or health change. No agent call traverses the registry at runtime. This gives governance without adding latency.

P4 — Context by Envelope, Not Full History Propagation

Passing full conversation history across orchestrator boundaries is expensive, potentially leaks sensitive context across pillar boundaries, and creates enormous token overhead at scale. The Enterprise Orchestrator extracts a semantically compact Context Envelope — intent summary, user identity, regional context, and ≤3 semantically relevant prior turns — before routing to any domain orchestrator.

P5 — Deterministic Chains for Governed Processes

Finance and HR process agents execute in deterministic sequential chains (Google ADK SequentialAgent pattern), not LLM-driven dynamic routing. The LLM determines what to do; the orchestration structure determines how it executes. This is non-negotiable for SOX auditability (Finance) and GDPR compliance (HR). Every step is checkpointed to durable storage before execution.

P6 — Model Tiering as Architectural Design, Not Optimization

Every agent in the system is assigned a model tier at design time: Haiku-class for intent classification and data retrieval, Sonnet-class for domain orchestration and analysis, Opus-class for cross-domain synthesis and novel insight generation. Escalation paths are defined for when complexity exceeds the assigned tier. Model cost and latency are architectural constraints, not afterthoughts.

P7 — Least Privilege Identity by Default

Every agent has a unique service identity with credentials scoped only to the tools it is explicitly permitted to call. A Sales SQL Agent has read-only access to the sales data mart and nothing else. A Finance Process Agent has write access to Oracle Finance APIs in its approved process scope only. Shared service accounts are prohibited for any agent with external system access.

What's New — The Insight Engine

Insight Engine — The Architectural Innovation

The Insight Engine is not a single agent. It is a ParallelAgent fan-out that dispatches to multiple domain SQL agents simultaneously, then pipes all results into a dedicated Insight Synthesizer LLM (Opus-class) with access to external market signals.

Triggered by the Analytics Orchestrator when: (1) query spans multiple domains, (2) user asks "why" or "what drove", (3) explicit analysis request, or (4) KPI deviation exceeds defined threshold.

Critical Design: Graceful Degradation on External Data Failure

The External Market Intelligence call has a hard 3-second timeout. On timeout or API failure, the Insight Synthesizer runs with internal data only, appending a data-availability flag to the output. The user still receives meaningful insight — the absence of external context is surfaced transparently, not silently dropped or propagated as an error. This is an SLA contract defined in the Agent Registry.

External Market Intelligence Agent

Dedicated agent (Sonnet) that integrates with:

  • Commodity price indexes (beef, chicken, packaging)
  • Macroeconomic indicators (CPI, consumer confidence, unemployment by region)
  • Weather data (relevant for drive-thru / outdoor dining patterns)
  • Consumer sentiment feeds
  • Competitive activity signals (new entrants, promotional events)

Critical: This data does NOT live in the enterprise data warehouse. This is the gap that makes current analytics incomplete. External data is fetched at query time via MCP-compliant tool integrations, not pre-loaded.

Historical Benchmark Agent

Provides context that raw query results lack:

  • Same-store sales comps (YoY, QoQ, by region and tier)
  • Peer store cohort benchmarking (store performance tier)
  • QSR industry benchmarks (if licensed data is available)
  • Fiscal calendar context (holiday weeks, promotional periods)

This agent reads exclusively from the enterprise data warehouse. It is a Haiku-class domain agent, not an insight agent. It provides inputs to the Insight Synthesizer, not conclusions.

Critical: Checkpointing Before Every ERP/HRIS Write

Every process agent checkpoints its full execution state to a durable store (Redis + PostgreSQL) before any write to Oracle Finance or SAP SuccessFactors. If the write fails, the agent resumes from the checkpoint — not from the beginning. If a step is rejected at the human approval gate, the state is captured with rejection reason and the workflow is terminated cleanly with a full audit log. There is no "retry from scratch" pattern for write operations to systems of record.

Process Agents + Data Warehouse: The Bridge

Process agents frequently need data warehouse context (e.g., the AP/AR agent needs supplier purchase history; the Talent Acquisition agent needs headcount targets). This is handled via a shared Data Access Tool — a scoped, read-only MCP tool registered in the Agent Registry that any authorized agent can call. Process agents do NOT directly invoke SQL agents. They call the Data Access Tool with a structured query schema. This keeps the process pillar decoupled from the analytics pillar's internal routing logic.

Session & Context Architecture

Context Envelope Pattern

Rather than forwarding full conversation history across orchestrator boundaries, the Enterprise Orchestrator constructs a Context Envelope for each downstream domain orchestrator:

  • User identity + role + regional scope
  • Intent summary — compressed statement of what the user needs
  • Relevant prior turns — semantic retrieval of ≤3 turns related to current intent (not sequential history)
  • Active business context — current fiscal period, active escalations, user's domain focus
  • Cross-pillar flags — is the analytics pillar currently processing a related query?

Result: domain orchestrators get rich context without token explosion. A full 40-turn session becomes a ~500-token envelope.

State Scoping (Google ADK Model)

ScopePrefixWhat Lives Here
Invocation temptemp:Scratch data for this single agent invocation. Never persisted.
Session(none)Current conversation state, active intent, intermediate results.
Useruser:Preferences, role, region, language, notification settings. Persists across sessions.
Appapp:Fiscal calendar, global KPI benchmarks, active incidents. All users see the same values.

Session persistence: DatabaseSessionService (PostgreSQL) for all production deployments. InMemorySessionService for local dev only. Vertex AI Agent Engine provides managed session storage at GCP scale.

Long-Term Memory Strategy

Vector Store (Semantic Memory)
Stores embeddings of: prior insight narratives, resolved investigation summaries, user query patterns. Retrieved at session start by semantic similarity to current intent. Powers the "relevant prior turns" selection in Context Envelopes. Chunked + deduplicated weekly.

Structured KV Store (Factual Memory)
Stores: known business benchmarks, fiscal calendar, store tier classifications, active regulatory flags per region. Read by the Enterprise Orchestrator to populate app-scoped state before every session. Updated by automated data pipeline, not agents.

Agent Registry & Discovery Governance

Decision: Centralized Catalog + Distributed Runtime Discovery

Industry research confirms: centralized registries for governance, distributed caching for runtime performance. At 44K restaurants generating analytics traffic, any per-request registry lookup is a bottleneck. Each orchestrator caches the registry at startup. Health state changes are pushed via event stream (not polled). New agent deployments invalidate orchestrator caches automatically.

What the Registry Stores Per Agent

  • Name, version, description (critical for LLM routing)
  • Input / output schemas (JSON Schema)
  • Declared P95 latency SLA
  • Compliance tags (SOX, GDPR, PCI, PII)
  • Required auth scope
  • Owner team + on-call contact
  • Upstream dependencies
  • Deprecation status + successor agent

Runtime Discovery Flow

  • Orchestrators load registry snapshot at startup
  • Registry pushes health delta events on: agent deployment, health check failure, SLA breach
  • Orchestrators apply delta in-memory (no restart)
  • No agent call touches the registry at runtime
  • Compliance checks happen at the Gateway layer using registry metadata — not at agent call time

Agent Versioning Policy

  • Semantic versioning: MAJOR.MINOR.PATCH
  • Breaking schema changes → MAJOR version. Old version kept alive for 30-day migration window.
  • Prompt-only changes → PATCH version. Old orchestrators still route to compatible version.
  • A/B testing: registry supports traffic split annotations (e.g., 90% v1.2, 10% v1.3-experimental)
  • Rollback: previous version never deleted until new version passes 7-day stability gate

Security Architecture

Agent Identity & Least Privilege

  • Every agent has a unique service identity (OIDC token or Workload Identity on GCP)
  • Analytics agents: read-only access to their assigned data mart only
  • Process agents: scoped write access to their assigned external system, defined process scope only
  • Enterprise + Domain Orchestrators: access to invoke sub-agents only — no direct data access
  • Credentials are rotated automatically; agents never hold long-lived secrets
  • Per-agent audit logs are non-repudiable (append-only, signed)

Prompt Injection Defense

At enterprise scale, adversarial content in external data sources (market intelligence APIs, user-submitted data, restaurant notes) can hijack agent behavior. Defenses:

  • Input sanitization at the Gateway — strip prompt-like patterns from user input
  • Tool output validation — external data tool results are schema-validated before being passed to LLM context
  • Instruction hierarchy — system prompts are injected at the infrastructure layer, not the user input layer
  • Output validation — structured output schemas enforced at inference time (constrained decoding)
  • Regular red-team exercises against production agent chains

Regional Compliance Routing

The Agent Gateway enforces regional routing based on the user's authenticated regional scope. EU users: agent calls are routed to EU-deployed agent instances. HR data (GDPR-sensitive) never leaves the declared processing region regardless of which orchestrator initiates the call. The compliance tag in the Agent Registry triggers this enforcement automatically. No agent needs to know about GDPR — the infrastructure layer handles it.

Observability Architecture

Distributed Tracing (OpenTelemetry)

Every agent invocation — from Enterprise Orchestrator down to individual SQL agent — carries a propagated trace context. A single user query produces a trace spanning the full agent chain: intent classification → domain orchestrator → parallel SQL agents → synthesizer. Traces exported to a centralized Collector (not per-agent sidecars). Tail-based sampling: 100% for errors and SLA breaches, 5% for normal traffic.

Cost & Token Budgets

Token usage tracked per trace, per agent, per user, per domain, per day. Per-request max_tokens enforced at the Gateway. Per-session token budgets block runaway loops. Model tiering decisions are validated against actual cost data monthly. Any agent consistently exceeding its budget triggers a prompt/model review.

Business KPI Correlation

Agent operational metrics (latency, error rate, insight quality scores) are correlated with business outcomes (user retention, query satisfaction ratings, process completion rates). This is the feedback loop that justifies model upgrades or agent redesign. Without this correlation, the architecture drifts based on engineering intuition rather than business evidence.

Latency Mitigation Strategies

Prompt Caching

System prompts, business context, and agent descriptions are stable content — cached at the provider layer (Anthropic prompt caching, GCP Vertex caching). High-frequency queries against the same KPI domain reuse cached prompt prefixes. Estimated 40–60% cost reduction on repeat analytical workloads.

Async Processing for Non-Interactive Workflows

Process automation workflows (AP/AR processing, period close, workforce planning) are submitted to an async queue (Pub/Sub or Kafka). Users receive a job ID and webhook notification. The synchronous response path is reserved for interactive query-response cycles only (<10s SLA).

Circuit Breakers + Graceful Degradation

Each agent boundary has a circuit breaker. On failure: (1) exponential backoff with jitter, (2) fallback to cached results if available, (3) graceful partial response with explicit data-availability flag, (4) never a silent failure. ERP and HRIS calls use the shortest timeout budgets — external system latency does not propagate to the user.

Architectural Self-Critique

Where This Architecture Could Fail

Architecture quality is judged not only by what it gets right but by how honestly it accounts for where it will be wrong. The following are this architecture's genuine failure modes — not theoretical risks but structural vulnerabilities that require active mitigation.

Risk 1: Enterprise Orchestrator Becomes a God Agent Over Time

The Enterprise Orchestrator starts as a thin meta-router. Within 12 months, as teams ask for "just one more routing rule" or "just handle this edge case here," it accumulates business logic from every domain. This is the most common failure mode in multi-tier architectures. Once business logic enters the enterprise layer, it cannot be cleanly extracted without a full rewrite.

Mitigation:

Enforce an architectural fitness function: the Enterprise Orchestrator's prompt file has a maximum token budget (enforced in CI). Any business logic addition is flagged by PR review policy. Quarterly architecture audits check for domain-specific terms in the enterprise orchestrator's prompt.

Risk 2: Context Envelope Loses Critical Prior Turns

The Context Envelope compresses session context to improve performance. But semantic retrieval of "relevant prior turns" can miss critical but semantically distant context. If a user spent 10 turns analyzing a financial anomaly and then asks a process automation question, the Finance Process Orchestrator may not receive the analytical context that makes the process request meaningful. The envelope is an approximation, not a guarantee of context fidelity.

Mitigation:

The Enterprise Orchestrator maintains the full session store. If the process result lacks coherence with session history (detected by a lightweight consistency checker), it can re-request the envelope with an expanded prior-turns window. The fallback is slower but correct. Context Envelope quality is a measured metric in the observability layer.

Risk 3: Process Agent Scope Creep — Permissions Accumulate Over Time

Process agents are launched with narrow, scoped permissions. As new use cases emerge, teams add permissions incrementally rather than creating new scoped agents. Within 18 months, agents that started with single-process authority end up with access to multiple ERP modules, broad read access to sensitive HR data, and write permissions that span their original design intent. This is not a hypothetical — it is the observed pattern in every enterprise automation initiative.

Mitigation:

Permission sets for every process agent are defined in the Agent Registry and enforced by the credential management layer — not by the agent's prompt. Adding a permission requires a registry update + security review + approval from the data owner. Agents cannot accumulate permissions through prompt changes alone. Quarterly least-privilege audits compare declared permissions against observed usage via audit logs.

Risk 4: The Insight Engine's External Data Dependency Degrades SLA

The Insight Engine's value depends on external market intelligence. As the system matures, the team will want to add more external data sources, increase their freshness, and reduce the timeout threshold from 3 seconds. Each of these increases the risk that the external data path degrades the SLA for the entire Insight Engine invocation. External APIs are significantly less reliable than internal data warehouse queries.

Mitigation:

External data calls are structurally isolated in a dedicated External Market Intelligence Agent with its own circuit breaker, separate from the internal data fan-out. The Insight Synthesizer is designed to produce high-quality output from internal data alone; external data is enhancement, not prerequisite. Pre-fetch and cache high-frequency external data (commodity prices updated every 15 minutes) to eliminate real-time latency for common insight types.

Risk 5: Agent Versioning Complexity Becomes Unmanageable at Scale

With 20+ specialized agents across two pillars, versioning creates a combinatorial compatibility problem. When the Finance Process Orchestrator references the Budget Variance Agent at v1.2, and the Analytics Orchestrator references the Finance Data Agent at v2.0, and the Insight Synthesizer has its own version — managing the compatibility matrix across all of these becomes a full-time engineering function, not a policy.

Mitigation:

Define "interface stability contracts" — agents guarantee backward compatibility on their declared input/output schemas for a minimum 90-day window. Breaking changes require a new agent name, not a new version number. The registry enforces this by preventing same-name schema breaks without a MAJOR version bump. Automated compatibility testing in CI validates that every orchestrator's declared dependency tree is internally consistent.

Risk 6: The Architecture Underestimates Cross-Regional Complexity

The architecture currently handles regional compliance via Gateway routing and compliance tags in the registry. But the complexity of 44,000 restaurants across regions is deeper: EU and APAC data residency laws prohibit certain cross-border data flows even within the analytics pillar. A cross-domain insight that combines EU customer data with global supply chain data may be a GDPR violation depending on how it's processed. The architecture documents this as a compliance tag but does not fully specify the enforcement logic.

Mitigation:

Phase 3 explicitly includes GDPR-compliant regional deployment architecture. In the interim, compliance tags in the registry must include data-residency constraints (not just sensitivity labels), and the Enterprise Orchestrator must enforce data-residency boundaries when constructing cross-domain requests. This requires legal input to the registry metadata schema — it cannot be designed by engineering alone.

What This Architecture Is NOT

This is not an AI-first architecture that wraps existing processes in a chat interface. It is not a RAG system over documents. It is not a single AI assistant with many tools. It is a federated multi-tier agent fabric where each agent has a specific, bounded responsibility within a defined governance structure, connected by explicit protocols, observable end-to-end, and extensible without requiring changes to existing components. The difference matters: architectures designed as "AI wrappers" hit ceilings at the complexity of a single agent's context window. This architecture's ceiling is the complexity of the business itself.
